# Relaxed MMIO 验证

2026-09-23 按用户要求恢复标准 `readl()`、`writel()` 访问，保留启动前的
`wmb()`。当前源码的完整提交、dirty bitmap 提交和寄存器 2 均使用
`vdpu_write()`。本次仅进行离线构建，后文保留 2026-09-22 的实验记录。

实验版本的 `th1520_vdec_start()` 配置批量写入使用 `writel_relaxed()`，覆盖完整
寄存器提交与 dirty bitmap 分支，末尾保留 `wmb()` 和普通启动写入。
IRQ 完成读取、确认和复位维持原有访问方式。目标 Linux `6.6.140-th1520`
的 RISC-V 头文件与模块反汇编确认，默认完整提交每帧减少 510 次普通写的前置 fence，
DMA 数据与配置仍在启动前发布。

2026-09-22 使用 FFmpeg Request、两份连续 1080p 6000 帧输入，普通与
relaxed 模块交替测量三轮，各次切换后先预热 600 帧。速度测试保留
`drm_prime` 硬件帧并使用 null 输出，包含进程启动、探测和退出开销。

| 编码 | 普通 MMIO | relaxed MMIO | 中位数变化 |
| --- | ---: | ---: | ---: |
| H.264 | 381.17 fps | 382.26 fps | +0.29% |
| HEVC | 504.00 fps | 504.91 fps | +0.18% |

每轮分别约 15.7 秒和 11.9 秒，十二次正式运行共 72000 帧全部完成。
本次观察到的差异很小；这些数值使用新的连续长输入，MMIO 效果按同表中的
两种模块比较。

基础像素、1080p、混合 context、Request 并发及截断后恢复通过；
`v4l2-compliance 1.28.1` 为 56/56，失败和警告均为零。
独立故障注入模块丢弃一次完成通知，watchdog 在 2242 ms 后返回 ERROR，
同一 context 的下一帧 6144 字节全部匹配。注入模块随后卸载，恢复正常
relaxed 模块，2 worker、20 轮再次通过。硬件持续忙碌时的 abort 轮询
仍需单独验证。

测试保持临时模块加载，系统模块安装目录、启动配置与设备树保持原样。
